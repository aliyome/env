# explainer-video

調べた内容を、初めての人にも分かる解説動画にする。台本（`script.json`）を1つ書けば、音声の合成・シーンの長さ・字幕・図の出るタイミングが自動で揃う。

```
台本 script.json（文ごとの字幕・読み・図の指定）
  → scripts/gen_voice.py（文ごとに音声を合成し、長さを測って timeline.json を作る）
  → scripts/build_video.py（台本と timeline.json から HyperFrames のプロジェクトを書き出す。シーンごとに1つのサブコンポジション）
  → HyperFrames（lint・snapshot で確認 → MP4 に書き出し）
```

HyperFrames は HTML と GSAP のタイムラインから動画を書き出すツール（Apache-2.0）。`<skill>` はこの SKILL.md があるフォルダを指す。

## 0. 前提を確かめる

次の5つを確かめる。

```bash
node -v                                   # 22 以上
uv --version
ffmpeg -version | head -1
curl -sf http://localhost:11180/ >/dev/null && echo ok  # speech.cpp (speech serve)
df -h .                                   # 作業フォルダの空き容量
```

- Node.js・uv・ffmpeg のどれかが無いときは、`brew install node uv ffmpeg` を示し、実行してよいかをユーザーに聞いてから実行する。
- `speech` サーバー（`http://localhost:11180`）が応答しないときは、次のコマンドで起動するよう案内して止まる。
  `speech serve --port 11180 irodori-tts --add-voice="narrator=/Users/aliyome/repos/kikuhon/voices/irodori-tts/narrator.voice.gguf" --voice="narrator"`
- 空き容量（`df -h .` の Avail）が 2GB を切っていたら、ユーザーに空けてもらってから進める。HyperFrames の `render` は空きが 1GB を切ると書き出しを拒否する。
- **sandbox の外で実行するもの**: `hyperframes check`・`snapshot`・`render` はヘッドレスブラウザを使い、sandbox の中では `mach_port ... Permission denied` で落ちる。最初から sandbox の外で実行する。`npm i` と `pdf_page.py` の初回（pymupdf を入れる）はネットワークが要る（npm のレジストリと pypi.org・files.pythonhosted.org。`allowed_domains` に足すか sandbox の外で実行する）。
- 音声は MCP を使わず、`speech serve` の OpenAI 互換 API（`POST /v1/audio/speech`、`response_format: "wav"`）を直接呼ぶ（`gen_voice.py` がやる）。
- HyperFrames は既定で匿名の利用状況を PostHog に送るので、すべての `hyperframes` コマンドに `HYPERFRAMES_NO_TELEMETRY=1` を付ける（環境変数は設定ファイルより優先される）。`snapshot` は `GEMINI_API_KEY` があると画像を Gemini に送るので、`--describe false` も付ける。`hyperframes feedback` は実行しない。
- HyperFrames の公式スキルは、手順7で `npm i` したあと `node_modules/hyperframes/dist/skills/`（`hyperframes`・`hyperframes-cli`・`media-use`）で読める。動きや CLI で迷ったら読む。動きは GSAP の止めたタイムライン（`paused: true`）で作る。CSS の transition / animation は書き出しで動かない。

## 1. 長さ・対象者・音声を選んでもらい、参考資料を受け取る（必ず最初に）

AskUserQuestion で次の3つをまとめて聞く。そのあと4つ目を聞く。依頼文にすでに答えが書かれている項目は聞き直さない（全部そろっていれば質問せずに進む）。

1. **長さ**: 「5分（要点だけ）」「10分（標準）」「20分（網羅的）」など。目安は1分あたり8〜9文（1文25〜30字前後で測った実績）。5分なら40〜45文、10分なら80〜90文、20分なら160〜180文。
2. **対象者**: 「非エンジニア・初めての人」「エンジニア」「意思決定者（数字と結論）」「専門職」など。対象者で書き方を変える（下の表）。
3. **音声**: `speech serve` に登録した話者名から選んでもらう（既定は `narrator`、ほかは「その他」で受ける）。台本の `voice` には**話者名（文字列）**を入れる。
4. **参考にするコードのリポジトリ・資料**（あれば）: AskUserQuestion で「ある（次のメッセージでパスや URL を貼る）」「ない」を聞く。ある場合は、ローカルのパス、GitHub のリポジトリや PR の URL、Notion・PDF・Slack などの URL を受け取る。依頼文にすでに書かれていれば聞き直さない。**コードは特に重要な素材として扱う**（仕組みの説明は、実際のコードで裏が取れると正確になる）。

| 対象者                   | 書き方                                                                              |
| ------------------------ | ----------------------------------------------------------------------------------- |
| 非エンジニア・初めての人 | 用語は出たところで一言説明。目的 → 全体像 → 仕組み → 細部の順。架空の例と数字で追う |
| エンジニア               | 仕組みとデータの流れを中心に。識別子やファイル名を補足に出してよい                  |
| 意思決定者               | 結論と数字を先に。判断に要る論点と未決事項を明示                                    |
| 専門職                   | 用語・制度・数値の正確さを優先。根拠の資料名を画面に出す                            |

## 2. 作業フォルダを作る

集めた画像や台本の置き場所を、先に作っておく。

```bash
mkdir -p <作業フォルダ>/<動画名>/assets/shots && cd <作業フォルダ>/<動画名>
cp -n <skill>/assets/script.example.json script.json   # -n: 既にある台本は上書きしない
```

以降のコマンドは、すべてこのフォルダで実行する。

## 3. 事実を集める

- 推測で台本を書かない。公式資料や手元の資料で裏取りした事実シートを先に作る。調べものが多いときはサブエージェントに分けて並列にする。
- 確かめられないことは、言い切らずに「未公表」「はっきりしない」と言う。
- 資料どうし（例: 社内資料と公式資料）で食い違う事実や、裏取りに要る MCP が使えないときは、片方の資料だけを信じて進めない。事実シート（`facts.md`）でその事実に「要確認」と書き、ユーザーに伝える。
- **受け取ったコードは必ず読む。** 説明する仕組みの入口（エントリポイント・主要な関数・データの流れ）を追い、動画で見せる抜粋を5〜20行ずつ選ぶ。抜粋は実物からコピーし、`リポジトリ/パス:開始行-終了行` とコミット SHA（`git rev-parse HEAD`）を控える。読んでいないコードについて推測で語らない。
- 受け取った資料（PDF・Notion・Slack など）も読み、事実シートに出典付きで入れる。
- 実物の画面・書類があると格段に分かりやすい（「言葉だけでは分からない」と言われやすい）。PR に貼られた動作確認キャプチャ、公式 PDF のページ、モックの画像などを `assets/shots/` に集め、`assets/shots/index.md` に出典を書く。個人情報や実在の ID が写っているものは使わないか、架空の値に置き換える。
- PDF のページは `uv run <skill>/scripts/pdf_page.py <pdf> <ページ> assets/shots/<名前>.png` で画像にする。まずページ全体を出して見て、要る部分を `--crop x,y,w,h`（ページ左上からのポイント単位。ページの大きさは出力に出る）で切り出す。初回は pymupdf を入れるのでネットワークが要る（手順0）。

## 4. 台本を書く（script.json）

**書き始める前に `references/script-format.md` を読む。** 項目（`sentences`・`readings`・`visual`）、レイアウト、部品、自作の図の書き方はそこにある。特に守ること: 1文36字以内（半角は0.5字で数える）、シーンの `id` は小文字の英数字とハイフンだけ。

**見せ方の方針: インフォグラフィックとキャプチャを多めに使う。** 視聴者は、書類名や画面名を言葉だけで説明されても分からない。実物のキャプチャを見せてほしい、という声が多い。目で見て分かる画面を、話の中心に置く。

- どのシーンにも、図かキャプチャを1つ以上置く。字幕だけのシーンや、文字を並べただけのシーンは作らない。
- 中身に合わせて図の形を選ぶ。数字は `big`、手順や時間の流れは `steps` か時間軸、比較は表や左右に並べた図、関係は図解にする。
- 実物があるものは、説明より先に実物を見せる。書類、画面、ファイルの中身、コードが対象になる。動画全体で、少なくとも3割のシーンに実物のキャプチャかコード抜粋を入れる。集め方は手順3を参照。
- 図の種類が用意された部品で足りないとき（時間軸、対応表、注釈付きの書類など）は、自作の図を作る（script-format.md の「自作の図」）。

## 5. 読みやすさを確かめる（別のサブエージェントに読ませる）

台本を書いた本人は、自分の文の分かりにくさに気づきにくい。**台本を書いたのとは別のサブエージェント**を立て、全文を読ませて直し案を返させる。

- サブエージェントには `script.json` のパス、頼まれた長さ、いまの合計（文の数と、1分あたり8〜9文で割った分数。gen_voice.py を実行済みなら最後の `total`）、下のチェックリストを渡す。`yomiyasu` スキルが使える環境なら、それも invoke させる。
- 返事は「文の場所｜元の文｜直した文｜理由｜必須か任意か」の表で受け取る。
- 必須の指摘を台本に反映し、もう一度読ませる。**最大2周**。2周目のあとも残った必須の指摘は、最終報告でユーザーに伝える。
- 直しで文が増えて長くなりすぎたときの扱いは、手順7の「長さ」に従う。

ナレーションのチェックリスト（耳で聞いて分かるか）:

- 文の中にカッコを入れない。補足は別の文にする。
- 耳で聞くと区別できない同音異義語を避け、言い換える（改定と改訂、市立と私立 など）。
- 1文に1つのことだけ言う。
- 主語をはっきり書く。
- 1文36字以内（半角は0.5字で数える）。字幕が2行を超えない。
- 数字と単位が自然に読めるか（「3つ」「1行」「2022年」など。読みは手順6で確かめる）。
- 比喩の動詞・絵文字・ダッシュ・文末のコロンを使わない。
- 尺に余裕がないときは、文を分ける・足す提案は任意扱いにする（必須にしない）。

## 6. 読みを確かめる

`uv run <skill>/scripts/check_readings.py` で、読み辞書を適用したあとの TTS 入力文を全文出す（台本の既定は `script.json`）。`speech` には事前のカタカナ読み確認 API がないため、辞書適用後のテキストを見て誤読しやすそうな語を洗い出す。

読み辞書は3つあり、`gen_voice.py` と `check_readings.py` が自動でまとめて使う。下ほど優先する。置き換えは1回で、長い語が先に当たる。英数字だけの語は単語の切れ目でだけ当たる（`PI` は `API` の中では読み替えない）。

1. スキル同梱の辞書 `<skill>/references/readings.json`: 文脈で読みが変わらない語（製品名、既定値 など）。
2. ユーザーの辞書 `~/.config/explainer-video/readings.json`: その人が足した語。スキルの外にあるので、スキルを更新しても消えない。
3. 台本の `readings`: その動画だけの読み。

文脈で読みが変わるので辞書に入れず、台本の `readings` で直す誤読:

| 書き方                       | 誤読       | 直し                               |
| ---------------------------- | ---------- | ---------------------------------- |
| 2022年（数字＋年が文中で）   | 〜トシ     | にせんにじゅうにねん               |
| 前と後                       | ゼントアト | まえとあと                         |
| 行った分                     | イッタブン | おこなった分                       |
| ①②・→ などの記号             | 記号のまま | 言葉に置き換える（ユーザーに確認） |
| 英字略語（SaaS、OAuth など） | 揺れる     | ユーザーに読み方を確認する         |

**怪しい読みは、ユーザーに質問して確定するまで音声を合成しない。** 次のどれかに当たる語は「怪しい読み」として扱う。

- 上の表にある語、またはそれと同じ型（漢字の音読みと訓読みが割れる、数字＋助数詞、記号）
- 英字の略語・製品名・固有名詞のうち、そのままでは読みが揺れやすい語や、読み方が複数通り広く使われている語（例: SaaS、OAuth、社名）。英字の語をすべて聞かない。読み辞書にある語は確定済みとして扱う
- check_readings.py の出力（読み辞書適用後）でも、文脈で自然な読みにならないおそれがある語
- 業界で読み方が分かれる語

確定のしかた: 怪しい語を集め、AskUserQuestion で1問に1語ずつ、候補の読みを2〜3個の選択肢にして聞く（4問まで。多ければ複数回に分ける）。答えを `readings` に入れ、check_readings.py をもう一度実行して、狙いどおりの読みになったことを確かめる。

**ユーザーに誤読を指摘されたら**:

1. 台本の `readings` を直し、check_readings.py で狙いどおりの読みになったことを確かめる。
2. 「共通の読み辞書にも足しますか？」と聞く。文脈で読みが変わる語（上の表の型）は足さない。
3. 足す場合は `uv run <skill>/scripts/yomi.py add <表記> <よみ>` でユーザーの辞書に追記する（初回はファイルを作る）。`~/.config` に書くので sandbox の外で実行する。次の動画からは自動で使われる。スキルの中の辞書は、スキルの更新で上書きされるので直さない。

ユーザーに質問できない状況（サブエージェントとして動いているなど）では、仮の読みで合成して先へ進めてよい。そのかわり `readings_questions.md` に「語｜候補｜仮に選んだ読み｜出てくるシーン」の表を書き、最終報告で確認を求める。確定したら readings を直して gen_voice.py を再実行する（変わった文だけ合成し直し、尺も自動で揃う）。

読み替えの注意:

- ②を「に」と読ませると、「②に」「②には」が助詞とまぎれる。台本で「②に」の形を避けるか、「②の手順に」のように名詞を挟む。

## 7. 音声を合成して書き出す

手順2の作業フォルダで実行する。

```bash
npm init -y && npm i -D hyperframes@0.8.139 gsap    # ネットワークが要る。sandbox で落ちたら sandbox 外で
uv run <skill>/scripts/gen_voice.py                 # assets/voice/<シーン>/<n>.wav と timeline.json
uv run <skill>/scripts/build_video.py               # index.html と compositions/<シーン>.html
HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes lint
```

- **lint の合格ライン: 0 errors、0 warnings。** build_video.py が書き出すファイルは warning も出ない。warning が出たら、まず `custom/` の自作の図を疑い、lint の `Fix:` に従って直す（例: 同じ要素に `fromTo` を2回以上かけるときは、いちばん早いもの以外に `immediateRender: false` を付ける）。直せない warning は、内容と理由を最終報告に書く。
- **長さ**: `gen_voice.py` の最後の `total`（分）が、頼まれた長さの ±15% に入っているかを確かめる。外れていたら、読みやすさの直しは捨てずに、優先度の低い文を削るかシーンをまとめ、gen_voice.py をやり直してから build する。
- `gen_voice.py` は、文ごとに wav を書き、長さを測ってシーンの尺（頭0.5秒、文の間0.3秒、末尾0.8秒）を決め、`timeline.json` に書く。文や読みを直したら gen_voice.py から再実行する。合成し直すのは、読み替えたあとの文・話者（`voice`）が変わった文だけで、残りは `assets/voice/cache.json` を見て前の wav を使う。読みを1語直しただけの再実行はすぐ終わる。
- `build_video.py` は、見出しと図の指定を `script.json` から読む。図だけを直したときは build_video.py だけ再実行すればよい（文が timeline.json と食い違うと止まる）。`warning:`（文が36字を超える、`at`・`until` が範囲外、画像が無い、知らない kind・layout・tone、コードの行が長くて折り返す・下が切れる）が出たら、台本を直して消す。
- 書き出したファイル（`index.html`・`compositions/`）は手で直さない。直すのは台本・`custom/`・作業フォルダの `theme.css`（下の「見た目」）。
- HyperFrames の版は、動作を確かめた 0.8.139 に固定している。上げるときは版番号を上げて `npm i` し、雛形の台本で build → lint・check が通ることを確かめてから、この手順の版番号も書き換える。

## 8. 見た目を確かめる

```bash
HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes check
HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes snapshot --at <秒,秒,...> --describe false -o snapshots
```

- `--at` には build_video.py が最後に表示する時刻（各シーンで全部の図が出そろったころ）を使う。snapshot は指定した時刻のあとに最後のコマを自動で1枚足す（PNG が1枚多いのはそのため）。動きの途中を見たいときは、`timeline.json` の文の開始時刻＋0.3秒前後も足す。
- `snapshots/contact-sheet*.jpg`（一覧）と各 PNG を Read で開き、文字のはみ出し・重なり・空白の偏り・画像の切れ・字幕と図の重なりを直す。

既知の落とし穴:

- シーンの背景は不透明のまま、中身だけをフェードしている。背景ごと消すと切り替わりで透明なコマができる。
- 書類や表の画像は枠に収まるように縮む（切れない）。縦に長い画面キャプチャは必要な部分を切り出してから使う。横長の画像の文字が小さいときも、レイアウトを変えるより先に切り出しを考える（script-format.md）。
- `hyperframes check/snapshot/render` はブラウザを使うので、sandbox の外で実行する（手順0）。

## 9. 仕上げ方を選んでもらう（Studio で確認・MP4 に書き出し）

build と lint（0 errors、0 warnings）が通り、手順8の見た目の確認が済んだら、AskUserQuestion で次の3つから選んでもらう。

1. **Studio で確認する**: 作業フォルダで次を実行する。`--background` は起動したらすぐ戻り、サーバーは裏で動き続ける。

   ```bash
   HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes preview --background --no-open --port=<空いている番号>
   ```

   出力の `Studio` の行の URL（`http://localhost:<番号>/#project/<フォルダ名>`）をユーザーに伝え、「ブラウザで開くと再生でき、Studio のタイムラインで直接直せます」と添える。sandbox の中では `open` でブラウザを開けないことがあるので、開いてあげようとせず URL を渡す。止めるときは `HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes preview --stop`（動いているかは `--status`）。build_video.py を再実行すると `index.html`・`compositions/` は作り直されるので、Studio での直しを残したいときは台本か `custom/` にも反映する。

2. **MP4 に書き出す**: 保存先を聞く（既定は `~/Desktop/<動画名>.mp4`）。次を background で実行する（1分の動画で数十秒）。

   ```bash
   HYPERFRAMES_NO_TELEMETRY=1 npx hyperframes render --quality looks --output <保存先>
   ```

   render は telemetry を切っていても最後に「Keep editing by chatting with Framey…」という宣伝の行を出す。害はないので無視してよい。書き出したら `ffprobe -v error -show_entries stream=codec_type:format=duration <保存先>` で長さと映像・音声の有無を確かめ、途中のコマを1〜2枚取り出して目で見る。

3. **両方**: 1 の URL を先に伝え、そのあいだに 2 を書き出す。

## 10. 残す

台本・`custom/`・`assets/shots/`・作業フォルダの `theme.css`（置いた場合）を git 管理の場所にコミットする。`assets/voice/`・`timeline.json`・`index.html`・`compositions/`・`assets/gsap.min.js`・`node_modules/`・`out/`・`snapshots/` は作り直せるので入れない。

## 動きの原則

上品でモダンに、派手にしない。動きの数値は `build_video.py` の先頭にまとめてある。

- 長さは0.3〜0.7秒。止まるときにゆっくりになる ease-out（`expo.out`・`power3.out`）を使う。
- 動く距離は小さく（最大24px程度）。下から少し浮き上がって現れる。
- 同じ文で出る複数の項目は、0.08秒ずつずらして順に出す。
- いま話している項目は、その文のあいだだけ、青の細い枠と柔らかい影で囲んで目立たせ、文が終わったら静かに戻す。
- `big` の数字は0.9秒で数え上がる。画像とコードは、わずかな拡大を伴って柔らかく現れる。
- シーンの切り替えは、中身だけが短く消えて次の中身が現れる（背景は動かない）。
- 跳ねる・回る・点滅する・繰り返す動きは使わない。
- 書き出しはタイムラインを1コマずつ動かして撮るので、時刻や乱数に頼る動きを書かない（同じ時刻はいつも同じ絵になる）。

## 見た目（テーマ）

- 見た目は `assets/theme.css` の1ファイルに集めてある（色・フォント・角丸・余白・文字の大きさ・`tone-*`）。レイアウトの `assets/base.css` は、theme.css の変数だけを読む。
- **1本の動画だけ見た目を変えるときは**、`cp <skill>/assets/theme.css theme.css` で作業フォルダにコピーして直す。build_video.py は作業フォルダに theme.css があればそちらを使う。変数名と `tone-*` のクラス名は変えない。スキルの中の css は直さない（ほかの動画にも効き、スキルの更新で消える）。
- 背景は薄いグレー、カードは白、文字は濃い紺。強調の色は青の1色だけで、`tone: blue` の項目の見出しと、話している項目の枠に使う。ほかの `tone` は無彩色なので、シーンが色分けで多色にならない。
- AIが作った感じに見える型（1辺だけの太い色線、塗りの番号バッジ、色付きの光る影、種類ごとの色の塗り分け）は使わない。
- フォントはヒラギノ角ゴシック（macOS 標準）。入っていない環境では Noto Sans JP などに代わる。
